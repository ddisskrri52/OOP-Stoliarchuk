nopCommerce (nopSolutions/nopCommerce) — платформа електронної комерції на C# (домен: електронна комерція). Коміт 4fa32aaffa6f.
Jellyfin (jellyfin/jellyfin) — медіасервер із серверною частиною на C# (домен: мультимедіа). Коміт e897d72b01f8. Усі номери рядків нижче відповідають цим зафіксованим версіям.
1. Приклади вдалого застосування SRP (Single Responsibility Principle)
Приклад 1: nopCommerce — CacheKey.cs
src/Libraries/Nop.Core/Caching/CacheKey.cs — рядки 17–42, 51–56.
Аналіз: Клас CacheKey представляє ключ кешу. Конструктор зберігає шаблон, а Create створює новий ключ, підставляючи перетворені параметри через string.Format. Клас не читає й не записує значення кешу: його відповідальність — представлення та формування ключа.
Переваги/Зміни: Формування ключів можна перевіряти окремо від сховища. Водночас початковий CacheTime залежить від конфігурації Singleton<AppSettings>. Для ключа з ідентифікатором магазину достатньо передати шаблон product.{0}.store.{1} і два параметри в Create; реалізацію зберігання кешу змінювати не потрібно.
Приклад 2: Jellyfin — SubtitleEditParser.cs
MediaBrowser.MediaEncoding/Subtitles/SubtitleEditParser.cs — рядки 31–82, 84–119.
Аналіз: SubtitleEditParser реалізує ISubtitleParser і відповідає за розбір субтитрів. Метод Parse читає переданий потік, вибирає відповідний парсер SubtitleFormat і повертає модель Subtitle. SupportsFileExtension перевіряє підтримку розширення. Клас не завантажує субтитри через HTTP та не запускає FFmpeg.
Переваги/Зміни: Логіку розбору можна перевіряти на підготовлених потоках без запуску медіасервера. Зміна повідомлень про помилки стосується Parse. Підтримка форматів залежить від бібліотеки SubtitleEdit: GetSubtitleFormatTypes шукає типи лише у збірці typeof(SubtitleFormat).Assembly, тому довільний клас з іншої збірки автоматично не підключиться.
2. Приклади порушення SRP (Single Responsibility Principle)
Приклад 1: Jellyfin — UserManager.cs
Jellyfin.Server.Implementations/Users/UserManager.cs — рядки 452–533, 623–675, 848–927.
Аналіз: UserManager поєднує побудову UserDto для API, застосування політик користувача та перевірки доступу під час входу із записом дат активності. GetUserDto, UpdatePolicyAsync і AuthenticateUser мають незалежні причини для зміни: контракт API, правила безпеки та збереження активності. Це дає підстави оцінити ці ділянки як порушення SRP.
Ризики/Зміни: Зміни різних вимог зачіпають один клас, збільшуючи обсяг перевірок і ризик регресій. Нове поле відповіді API потребуватиме зміни GetUserDto; нове обмеження доступу — перевірок у AuthenticateUser або UpdatePolicyAsync. Сам розмір файлу не доводить порушення SRP.
Приклад 2: nopCommerce — OrderProcessingService.cs
src/Libraries/Nop.Services/Orders/OrderProcessingService.cs — рядки 212–261, 824–902.
Аналіз: Клас координує замовлення, але також містить конкретні правила різних підсистем. AwardRewardPointsAsync визначає активацію та строк дії бонусів; SendNotificationsAndSaveNotesAsync вибирає одержувачів листів і підготовку PDF-вкладення. Окремі методи координують облік залишків. Незалежність правил бонусів і сповіщень створює кілька причин для зміни класу.
Ризики/Зміни: Поєднання правил у координаторі ускладнює підтримку. Нова умова строку дії бонусів потребуватиме зміни AwardRewardPointsAsync, а новий одержувач листа — SendNotificationsAndSaveNotesAsync. Координування саме по собі виправдане; ознакою порушення SRP є розміщення тут конкретних правил різних підсистем.
3. Приклади розширення за OCP (Open/Closed Principle)
Приклад 1: nopCommerce — платіжні плагіни IPaymentMethod
src/Libraries/Nop.Services/Payments/IPaymentMethod.cs — рядки 10–22; PaymentService.cs — 51–67; CheckMoneyOrderPaymentProcessor.cs — 16–60.
Аналіз: IPaymentMethod успадковує IPlugin і визначає ProcessPaymentAsync. PaymentService завантажує платіжний плагін через LoadPluginBySystemNameAsync і викликає його ProcessPaymentAsync. CheckMoneyOrderPaymentProcessor є реальною реалізацією цього інтерфейсу. Отже, видно контракт, конкретну реалізацію та місце її використання.
Переваги/Зміни: Обробка платежу відкрита для розширення, але закрита для модифікації в межах цього контракту. Новий сумісний шлюз додається як плагін, який потрібно встановити й активувати; наявний алгоритм виклику в PaymentService змінювати не потрібно. Сумісність плагіна та результати оплати слід перевіряти окремо.
Приклад 2: Jellyfin — підключення плагінів IPlugin
MediaBrowser.Common/Plugins/IPlugin.cs — рядки 11–57; PluginManager.cs — 106–140, 196–226, 592–605.
Аналіз: IPlugin задає спільний контракт плагіна. PluginManager.LoadAssemblies завантажує збірки ввімкнених і підтримуваних плагінів; CreatePlugins знаходить реалізації через GetExports<IPlugin>. CreatePluginInstance створює об’єкти через ActivatorUtilities, а RegisterServices підключає сервіси через IPluginServiceRegistrator.
Переваги/Зміни: Для сумісного плагіна використовується наявний механізм завантаження, тому алгоритм CreatePlugins не потребує нової гілки для кожної реалізації. Новий допоміжний сервіс можна зареєструвати через IPluginServiceRegistrator. Розширення обмежене доступними контрактами; сам IPlugin не забезпечує довільної функції. Ризик — несумісність API або залежностей.
4. Пропозиція рефакторингу для найгіршого прикладу
Ціль: UserManager.cs (Jellyfin). Серед розглянутих прикладів вважаю його найпроблемнішим через поєднання представлення даних API, політик доступу й запису активності. Пропоную поступове виділення відповідальностей, залишивши UserManager фасадом для наявних викликів. Наведені нижче назви компонентів є пропозицією.
Залишити в UserManager координацію сценаріїв, зберігши наявні провайдери автентифікації та механізм подій.
Винести побудову UserDto з GetUserDto в окремий UserDtoFactory, щоб зміни відповіді API мали окреме місце реалізації.
Винести застосування політик із UpdatePolicyAsync в UserPolicyService; перевірки дозволу на вхід оформити окремим компонентом правил доступу.
Винести запис LastLoginDate і LastActivityDate в UserActivityStore, зберігши умову isUserSession, блокування та узгодження об’єкта з базою. Перед перенесенням зафіксувати поведінку перевірками DTO, дозволеного й забороненого входу та дат активності. Це зменшить кількість причин змінювати фасад; межі транзакцій і порядок подій не слід змінювати без окремого обґрунтування.
Висновок
У роботі проаналізовано SRP та OCP у nopCommerce і Jellyfin. CacheKey та SubtitleEditParser мають чітко визначені відповідальності. UserManager і OrderProcessingService поєднують незалежні обов’язки, що ускладнює підтримку. Плагіни дозволяють додавати сумісні реалізації без зміни відповідного алгоритму ядра. Для UserManager запропоновано розділення відповідальностей зі збереженням поведінки системи.


Відповіді на контрольні запитання
1. Як відрізнити окрему відповідальність класу від просто великого обсягу коду?
   Відповідальність визначають за причинами для зміни класу. Кількість рядків сама по собі не доводить порушення SRP.
2. Які ознаки в коді найкраще підтверджують дотримання OCP?
   Можливість підключити нову реалізацію через спільний контракт без зміни наявного алгоритму.
3. Чому для аналізу SRP/OCP важливо дивитися не лише на інтерфейси, а й на місця
   Інтерфейсу недостатньо: важливо, як система підключає та викликає нові реалізації.
4. Які ризики виникають, якщо застосовувати рефакторинг “під патерн” без реальної потреби?
   Зайві абстракції ускладнюють код і його підтримку. Рефакторинг має розв’язувати конкретну проблему та зберігати поведінку системи.
