## Лабораторна робота №12 
# Тема: Обробка IO/мережевих помилок та патерн Retry. 
# Мета: Навчитися обробляти типові помилки вводу/виводу та мережеві помилки за допомогою блоків try-catch-finally, а також реалізувати патерн Retry для підвищення відмовостійкості застосунків.
# Висновок
У цій лабораторній роботі було успішно реалізовано обробку IO та мережевих помилок за допомогою патерну Retry з експоненційною затримкою. Принцип експоненційної затримки у моєму варіанті полягає у тому, що після кожної невдалої спроби запису у файл (IOException) або відправки на сервер (HttpRequestException) час очікування збільшується вдвічі. Це дозволяє ефективно розвантажити систему або мережу під час тимчасових збоїв, даючи їм час на відновлення перед наступним запитом.
# Відповіді на питання
1. Які типи винятків найчастіше виникають при роботі з файлами та мережею?
При роботі з файлами найчастіше виникають винятки вводу/виводу, такі як IOException (наприклад, файл заблокований іншим процесом), FileNotFoundException та DirectoryNotFoundException. При взаємодії з мережевими ресурсами типовими є HttpRequestException, SocketException та таймаути підключення.
2. Поясніть принцип роботи патерну Retry. Коли його доцільно використовувати?
Патерн Retry - це стратегія повторних спроб виконання операції, яка завершилася невдачею. Його доцільно використовувати для обробки саме тимчасових помилок (наприклад, короткочасна втрата інтернет-з'єднання, тимчасова недоступність файлу), які з великою ймовірністю можуть бути успішно вирішені самі по собі через кілька секунд.
3. Як реалізувати експоненційну затримку між повторними спробами?
Експоненційна затримка реалізується як стратегія збільшення часу очікування між спробами за геометричною прогресією. Практично це обчислюється множенням базового часу (початкової затримки) на 2 у степені номера поточної спроби.
4. Для чого потрібен делегат shouldRetry у допоміжному класі RetryHelper?
Делегат shouldRetry визначає, чи слід взагалі повторювати спробу для конкретного винятку.
