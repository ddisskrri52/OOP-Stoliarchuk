# Самостійна робота №20
## Тема: Реалізація exponential backoff.
## Мета: Розробити власний допоміжний клас для реалізації патерну Retry з експоненційною затримкою та випадковим “jitter”.
### Сценарій 1 (Успіх після невдач): 
У методі Execute операція штучно генерує виняток InvalidOperationException під час перших двох викликів. Клас RetryPolicy відловлює їх, логує причину та розраховує затримку за формулою експоненційного зростання з jitter. На третю спробу операція завершується без винятку, повертаючи очікуваний результат.
### Сценарій 2 (Остаточна невдача): 
Операція завжди кидає TimeoutException. Делегат shouldRetry дозволяє повторні спроби для цього типу помилки. Клас робить 3 повторні спроби (встановлений ліміт _maxRetries), щоразу збільшуючи час очікування, і після вичерпання ліміту остаточно прокидає виняток назовні.
### Межі застосування патерну Retry:
Патерн з експоненційною затримкою доцільно використовувати лише для тимчасових мережевих чи інфраструктурних збоїв. Його не можна застосовувати для помилок бізнес-логіки, постійних помилок доступу (наприклад, 403 Forbidden) або для неідемпотентних операцій без унікальних ключів транзакцій.
## Відповіді на питання
1. Чому експоненційна затримка зазвичай ефективніша за фіксовану для тимчасових збоїв?
Експоненційна затримка поступово збільшує час між запитами, даючи перевантаженому сервісу шанс на відновлення замість його постійного бомбардування.
2. Для чого потрібен jitter і як він зменшує ризик одночасних повторних спроб?
Jitter додає випадковий відсоток до розрахованого часу очікування. Це розсинхронізовує клієнтів і запобігає масовому одночасному надсиланню повторних запитів.
3. Яку роль відіграє делегат shouldRetry у власній реалізації політики повторних спроб?
Делегат shouldRetry дозволяє фільтрувати винятки, щоб виконувати повторні спроби лише для специфічних очікуваних помилок (наприклад, обрив з'єднання) та миттєво відхиляти критичні системні помилки.
4. У яких випадках повторна спроба не є безпечною та її слід заборонити?
Повторна спроба небезпечна для неідемпотентних операцій (переказ коштів, створення запису в БД), оскільки через мережевий збій клієнт може надіслати запит двічі, продублювавши дію.
