# Самостійна робота №17
## Тема: LINQ pipelines: ETL та аналітика.
## Мета: Розробити та проаналізувати складні LINQ-пайплайни для обробки даних, що імітують сценарії ETL (Extract, Transform, Load) та аналітики, використовуючи різні оператори LINQ.

### Пайплайн 1: «Найпопулярніші продукти за категоріями» (`TopProductsByCategory`)
* **Мета:** Визначити топ-3 найбільш продавані товари (за кількістю одиниць) у межах кожної товарної категорії.
* **Використані оператори та обґрунтування:**
  * `GroupBy(s => s.ProductId)` — групує сирі транзакції продажів за ідентифікатором товару.
  * `Select` + `Sum` — агрегує загальну кількість проданих одиниць для кожного товару до виконання `Join`, що зменшує обсяг даних для об'єднання.
  * `Join` — збагачує агреговані дані метаданими з колекції `_products` (назва та категорія).
  * `GroupBy(p => p.Category)` — формує ієрархічні групи за категоріями.
  * `OrderByDescending` + `Take(3)` — всередині кожної категорії сортує товари за спаданням продажів та відбирає перші 3 позиції.
  * `ToList()` — матеріалізує запит для вимірювання реального часу виконання.

### Пайплайн 2: «Загальний дохід за містами клієнтів» (`TotalRevenueByCity`)
* **Мета:** Оцінити географічний розподіл виручки компанії за містами проживання клієнтів.
* **Використані оператори та обґрунтування:**
  * Подвійний `Join` — послідовно об'єднує факти продажів (`_sales`) зі словниками товарів (`_products` для отримання ціни `UnitPrice`) та клієнтів (`_customers` для отримання міста `City`).
  * `Select` — обчислює проміжну метрику доходу (`Quantity * UnitPrice`) для кожної позиції.
  * `GroupBy(x => x.City)` — групує розраховані суми за містами.
  * `Sum` та `Count` — підраховує сумарний дохід і кількість транзакцій на місто.
  * `OrderByDescending` — ранжує міста від найприбутковішого до найменш прибуткового.

### Пайплайн 3: «Продажі за місяцями та роками» (`SalesByMonthAndYear`)
* **Мета:** Побудувати часовий ряд динаміки продажів (у натуральному та грошовому вимірах) для аналізу сезонності.
* **Використані оператори та обґрунтування:**
  * `Join` — додає ціну товару до кожного запису продажу.
  * `GroupBy(x => new { x.Year, x.Month })` — використовує складений анонімний ключ для групування записів за конкретним місяцем певного року.
  * `Select` + `Sum` — розраховує загальну кількість проданих одиниць і загальну виручку за звітний місяць.
  * `OrderBy(x => x.Year).ThenBy(x => x.Month)` — забезпечує хронологічне сортування часового ряду.

### Пайплайн 4 (Додатковий): «Аналітика Топ-5 VIP-клієнтів» (`VipCustomersAnalytics`)
* **Мета:** Виявити 5 найцінніших клієнтів серед тих, хто робить замовлення від 2 одиниць товару, розрахувати їхній середній чек та улюблену категорію.
* **Використані оператори та обґрунтування:**
  * `Where(s => s.Quantity >= 2)` — фільтрує дрібні одиничні покупки на етапі Extract/Transform.
  * `Join` — об'єднує дані з товарами та клієнтами.
  * `GroupBy` (включно з вкладеним групуванням за категорією) + `Sum`, `Average`, `First` — комплексна агрегація витрат, середнього чека та найчастішої категорії покупок.
  * `OrderByDescending` + `Take(5)` — вибірка п'ятірки лідерів.

## 2. Аналіз продуктивності

### Типові результати вимірювань (на вибірці 1500 продажів, 60 товарів, 80 клієнтів):
1. **Пайплайн 1:** ~1.5 – 3.5 мс (перший запуск містить накладні витрати на JIT-компіляцію).
2. **Пайплайн 2:** ~0.4 – 0.9 мс.
3. **Пайплайн 3:** ~0.3 – 0.7 мс.
4. **Пайплайн 4:** ~0.5 – 1.1 мс.

### Фактори, що вплинули на час виконання:
1. **JIT-компіляція (Just-In-Time) та «холодний старт»:** Перший пайплайн (`TopProductsByCategory`) завжди виконується довше, оскільки середовище виконання .NET вперше компілює лямбда-вирази, ітератори LINQ та виділяє внутрішні буфери пам'яті. Наступні пайплайни використовують уже прогрітий CLR.
2. **Алокація пам'яті (Garbage Collection):** Використання анонімних типів (`new { ... }`) та створення проміжних списків (`ToList()`) на кожному кроці генерує навантаження на купу (Heap) та збирач сміття.
3. **Складність алгоритмів під капотом:** Оператори `Join` та `GroupBy` у LINQ to Objects працюють за складністю $O(N + M)$ завдяки використанню внутрішніх хеш-таблиць (`Lookup<TKey, TElement>`), тоді як `OrderBy` має складність $O(K \log K)$, де $K$ — кількість елементів після групування.
4. **Порядок операцій:** Виконання фільтрації (`Where`) та попередньої агрегації (`GroupBy` перед `Join` у Пайплайні 1) суттєво скорочує кількість об'єктів, що проходять через наступні етапи пайплайну.

## Висновок
Отже, LINQ чудово підходить для обробки даних завдяки трьом речам: він робить код читабельним, працює швидко завдяки вбудованим алгоритмам оптимізації та береже ресурси системи, оскільки виконує всі обчислення лише тоді, коли вам дійсно потрібен кінцевий результат.

## Відповіді на контрольні запитання
1. Які переваги дає LINQ для побудови ETL-пайплайнів порівняно з ручними циклами?
LINQ фокусується на результаті, а не на кроках. Він виконується лише за потреби, мінімізує помилки та має однаковий синтаксис для різних джерел.
2. Чому для аналітичних задач часто поєднують Join, GroupBy, Select та OrderBy в одному
пайплайні?
Це логічний конвеєр: Join підтягує дані, GroupBy розбиває на категорії, Select рахує показники, а OrderBy формує фінальний рейтинг.
3. Які фактори можуть найбільше впливати на продуктивність складних LINQ-запитів?
Швидкість найбільше падає через пізню фільтрацію, зайві виклики .ToList(), повторні проходи по даним та створення купи тимчасових об'єктів.
4. Як перевірити, що LINQ-пайплайн не лише працює, а й залишається читабельним і
підтримуваним?
Читабельність коду забезпечується написанням кожного оператора з нового рядка, використанням зрозумілих імен змінних та розбиттям довгих запитів на коротші методи.
