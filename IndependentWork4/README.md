## Самостійна робота No4
# Тема: Розширення ієрархії та наслідки змін базового класу.
# Мета: Проаналізувати, як зміни в базовому класі впливають на похідні класи, та дослідити стратегії
розширення існуючих ієрархій наслідування.

# Висновок
На цій лабораторній я на практиці побачила проблему "крихкого базового класу": зміна лише одного параметра в конструкторі LibraryItem призвела до того, що довелося переписати конструктори всіх похідних класів (Book, Journal, AudioBook). Робота показала, що наслідування чудово підходить для поліморфізму, але робити зміни в базових класах на пізніх етапах розробки варто обережно, або ж надавати перевагу композиції.

# Відповіді на питання
1.Як зміна конструктора базового класу вплинула на похідні класи?
Зламала їхній код, оскільки виклики base(...) перестали відповідати новій сигнатурі конструктора базового класу і вимагали додавання нового параметра у всі нащадки.
2. Чим відрізняється розширення ієрархії через новий похідний клас від модифікації наявного базового класу?
Додавання нового класу (AudioBook) розширює систему і не ламає існуючий код (дотримується Open/Closed Principle), а зміна базового класу порушує роботу всіх наявних нащадків.
3.У яких випадках для цієї задачі композиція могла б бути кращою за наслідування?
Якби формати носіїв (паперовий, аудіо, електронний) змінювалися динамічно або поєднувалися. Тоді краще мати об'єкт LibraryItem, що містить деталі формату як окрему властивість.
4. Як поліморфний виклик DisplayDetails() допомагає перевірити правильність ієрархії?
Він дозволяє викликати метод через базове посилання LibraryItem, але при цьому виконується саме перевизначена версія класу-нащадка (override), що підтверджує правильне налаштування таблиці віртуальних методів (VMT).
